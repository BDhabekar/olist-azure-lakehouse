# Design decisions

[Back to the README](../README.md)

Each row has the option I turned down, because "why not the other way?" is the question I expect to be asked.

| Decision | What I chose | What I turned down, and why |
|---|---|---|
| On-premises access | Self-hosted integration runtime, outbound 443 only | Opening an inbound port or a public endpoint on the database |
| Where control metadata lives | An Azure SQL control database | Inside the source system, which the data team does not own |
| Incremental ingestion | Watermark on `modified_at`. The upper bound is read before the copy and saved after success. It is the newest change at least two minutes old, so a transaction still open at the source is picked up by the next run. Timestamps are passed to procedures as strings | A full reload every run. A `DateTime` parameter, which lost a millisecond and would have re-copied rows on every run |
| Type conversion in the copy | A conversion that would cut data fails the copy (`allowDataTruncation` off) | Data Factory's default, which truncates silently |
| Landing format | Parquet (snappy) in `load_date=` folders | CSV, which has no types and no schema |
| Silver write | Delta `MERGE` on the grain-census key, newest row per key, updated only when the incoming row is newer | Append (duplicates on a re-run). Overwrite (slow, loses history) |
| Silver read | A bookmark on `_loaded_at` | The Databricks standard is a streaming checkpoint: Auto Loader or Structured Streaming in PySpark, or a SQL streaming table, which runs on its own serverless pipeline. I kept plain SQL on a classic job cluster for cost, and I name it as an exception |
| Bad rows | Quarantine with the broken rule's name; good rows still load | Dropping them silently. Failing the whole load for one row |
| Reference tables | A stored row hash; a row is updated only when its content really changed | Rewriting every row on every run |
| Source times | `TIMESTAMP_NTZ`, because the source stores local time with no zone | `TIMESTAMP`, which shifts the value by the session time zone |
| Gold refresh | A full rebuild, worked out as views and reconciled with 13 checks before the tables are written. A failed check fails the run and leaves gold as it was | Incremental gold: at about 225,000 rows a rebuild is a handful of SQL statements and cannot drift. Overwriting first and checking afterwards: the alert would arrive with wrong numbers already published |
| Fact grain | Two facts (item and order), with payments summed per order | One fact joining payments to items, where the fan-out inflates revenue |
| Compute | A job cluster defined in the job (single node, D4s_v3). Development on a small all-purpose cluster with auto-stop | Serverless notebooks, which I measured as far more expensive for this workload |
| Job identity | A service principal per environment | A person's account |
| Orchestration | One Databricks job, started by Data Factory's Databricks Job activity | One Notebook activity per notebook |
| Environments | A separate resource group, factory, storage account, vault, control database, workspace, catalog and identity per environment | One environment, or prod in the same workspace as dev |
| Factory deployment | An ARM template generated by the build | The Publish button and the `adf_publish` branch |
| Pinned tools | The agent image, Node.js, the build package (lock file), the Databricks CLI, Bicep, and Python with the test packages are pinned in the repository. Azure PowerShell and the `SqlServer` module are not yet, which is a known gap | "latest", where a deployment can change because a tool did |
| Power BI | Import mode, with the `.pbip` in Git | DirectQuery (a cluster must stay up). The `.pbix` in Git (binary, and it holds data) |
| One table fails | Every other table still has its turn. The task fails at its end and the next layer does not start | Stopping at the first error, where one bad table holds back seven good ones |
| Failures that pass by themselves | The watermark lookup, the copy and the watermark update retry twice. One run of the pipeline at a time | No retry, where one network blip on the source machine fails the night's load |
| Tests | The real gold notebook, run on made-up rows by the build on the build machine's own Spark | Testing only by running in dev, where a wrong join is found after a cluster has been paid for |
